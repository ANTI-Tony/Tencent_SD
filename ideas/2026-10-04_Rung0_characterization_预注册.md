# Rung 0 预注册：投机解码 × drafter 在线自进化的资源冲突刻画

日期：2026-10-04（在看到任何测量结果之前写定；之后的改动必须在文末"变更记录"里注明日期和理由）
上游：2026-09-29_训练与投机联合算力分配_novelty_check.md
研究线（用户 10-04 定）：不训练新 drafter，而是在服务过程中由调度层决定何时允许现有 drafter 自进化。

## 0. 这一轮只回答两个问题

1. **冲突是否存在、在哪个负载区间存在**（实验 C1）：在同一张 GPU 上，投机的即时收益和在线更新的代价随负载怎么变？有没有一个负载带，更新的代价已经不可忽略而投机仍然有收益？
2. **在线更新多久回本、回本时间在不同 workload 之间差多少**（实验 C2）。

完整调度器、可插拔性、规模实验都不在这一轮。

## 1. 固定设置

- 硬件：OSC Cardinal，单卡 H100 SXM 94GB；每个作业 ≤1 小时（debug 分区）。
- 软件：vLLM 0.27.1（克隆自 BURSAR 的 bsr312 环境），EAGLE-3，草稿长度 k=3 固定（自适应 k 不在本轮范围）。
- 模型：M1 = Qwen3-8B（dense）+ AngelSlim/Qwen3-8B_eagle3；M2 = Qwen3-30B-A3B（MoE）+ AngelSlim/Qwen3-a3B_eagle3。M2 只进 C1 的 MoE 情形。
- 两种情形：R-short（非思考模式，对话/SQL/代码，输出 ≤512 token）；R-long（思考模式数学题，长输出 → 解码上下文长）。
- 演化规则 E1：AngelSlim 头的 teacher-forced 在线蒸馏（目标 = 目标模型实际输出的下一 token，草稿词表 CE）。每步 4096 token，AdamW lr 5e-5。第二种演化规则留到下一轮做可插拔性。

## 2. 实验 C1：负载 × 条件

- 条件：S0 不投机；S1 投机；S2 不投机 + 同卡训练进程；S3 投机 + 同卡训练进程（占空比 100%，另加一档 50% 只在 S3 跑）。
- 同卡训练进程：独立进程，在缓存的 aux hidden states 上训练头（只含头的前向反向，与真实共置系统里"hidden states 由服务免费给出"的开销一致）；默认分时共享（不开 MPS）。显存：S0/S1 用 gpu_memory_utilization=0.90；S2/S3 用 0.90 减去训练进程实测峰值占比——**KV 容量的损失算作共置成本的一部分**。
- 负载：先测 S0 饱和吞吐，再取其 5%–95% 之间 6 档泊松到达率；每档热身 20 s、测量 ≥150 s。
- 指标：输出 token/s、req/s、TTFT/TPOT 的 P50/P99、SLO 内 goodput（SLO 在冒烟测试后按 M1 低负载 P50 的倍数定死，写入变更记录）、平均接受长度（/metrics 的 spec_decode 计数器）、训练进程 token/s。
- 派生量：投机即时收益 Δspec(L)=goodput(S1)−goodput(S0)；更新代价 Δtrain(L)=goodput(S0)−goodput(S2)，以及 P99 TPOT 涨幅；交互项 I(L)=[goodput(S1)−goodput(S3)]−[goodput(S0)−goodput(S2)]。

## 3. 实验 C2：回本时间

- 域：A = 通用对话（ShareGPT），B ∈ {SQL（Spider）、代码、中文对话、函数调用 JSON}。
- 用 M1 对每个域生成"线上流量"（非思考、贪心）；前 N 条当作已观测流量用于更新，留出 300 条评测 B、300 条评测 A（遗忘）。
- 更新预算 K ∈ {0, 25, 50, 100, 200, 400, 800} 步；记录每步只含头的 GPU 时间 C_train(K)。
- 每个检查点用 vLLM 测：留出集接受长度；饱和吞吐下每请求 GPU 秒；低并发下 TPOT。
- 回本：T_be(K)=C_train(K)/s(K)，s(K)=饱和时每请求节省的 GPU 秒；报告成请求数和"按饱和到达率换算的分钟数"。低负载下另报延迟口径（TPOT 改善）。**低负载时训练的机会成本取 C1 实测的共置代价，不默认为 0。**

## 4. 预注册假设与判读

| 编号 | 假设 | 判为成立的条件 | 不成立时的含义 |
|---|---|---|---|
| H1 | 低负载共置不是免费的 | R-short/M1，L≤30% 饱和时，S2 相对 S0 的 P99 TPOT 涨 ≥20% | 涨幅 ≤10% → 低负载"空闲就训"（OSD 一句话）基本够用，低负载区间不需要调度器 |
| H2 | 投机收益有负载拐点且依情形而异 | R-short/M1 中 Δspec 在饱和前转为 ≤0；R-long 或 M2 中 Δspec 到 95% 饱和仍 >0 | 若三种情形拐点相同 → "情形依赖"这条论证作废 |
| H3 | 投机和更新争同一份余量 | 至少一个负载档上 \|I(L)\| ≥ Δtrain(L) 的 20% | I≈0 → 两者代价可加，联合调度退化为两个独立决策 |
| H4 | 回本时间跨 workload 差异大 | 4 个 B 域的 T_be(K=200) 最大/最小 ≥10× | <3× → 回本时间可用常数近似，"按回本决定训练"这一卖点变弱 |

## 5. 本轮的通过线（决定是否进入调度器阶段）

- 图 1 通过：存在一个负载带，Δtrain 不可忽略（goodput 降 ≥5% 或 P99 TPOT 涨 ≥20%）而 Δspec 仍 >0；且该负载带在至少两种情形里存在。
- 图 2 通过：H4 成立，且至少一个域在饱和负载下 T_be > 10 分钟、另一个域 < 2 分钟（"该不该训"随 workload 翻转）。
- 两图都不过 → 停止，按"训练与服务资源冲突在实测中不构成调度问题"写成负结果记录。只过一个 → 回报用户再定。
- 之后的 trace 回放（oracle 余量 K1、专用训练卡对比 K3）以本轮测得的曲线为输入，阈值沿用 2026-09-29 文档。

## 6. 已知局限（事先承认）

- 训练进程与服务分属两个进程，分时共享；真实系统可用同进程低优先级流或 MPS，干扰可能更小。本轮结果是"未做机制优化时的上界"。
- C2 用贪心解码测接受长度；采样解码下数值会变，方向不变的假设留待下一轮验证。
- debug 分区每作业 ≤1 小时，长输出情形的每档测量时间受限。

## 变更记录

- **2026-10-04（任何结果之前）C2 的预算单位改为"已消费请求数 N"，单遍在线**：原写法"K 步×4096 token"会让短输出域（SQL 每请求约 130 token）在 3200 条训练流量上被迫重复多轮，违背"在线、每条流量只学一次"的语义。改为 N ∈ {0,100,200,400,800,1600,3200} 条请求，每条只训一次（按到达顺序打包成约 4096 token 一步），C_train(N) 记录只含头的 GPU 时间。
- **2026-10-04（任何结果之前）aux 层约定**：读 vLLM 0.27.1 源码确认注册号 L = 第 L−1 层输出 = HF hidden_states[L]，故 M1 用 (2,18,33)、M2 用 (2,24,45)；冒烟测试用原装头做 teacher-forced 校准二次确认（对照 (3,19,34)）。
- **2026-10-04（任何结果之前）C1 负载轴用闭环并发数**（R-short：1–256；R-long：1,4,16,64,96），不用泊松到达率：并发数直接对应 batch 大小，每档稳态快；泊松版留作补充。
- **2026-10-04 冒烟测试之后（看到了冒烟的两档数字，正式主表尚未开跑）**：
  - 冒烟事实：校准 (2,18,33)=0.588 > (3,19,34)=0.544，沿用 (2,18,33)；训练进程峰值显存 10.5 GB → 预留改为 12 GB（原 14 GB）；原装头接受长度约 1.9（k=3）。
  - 冒烟看到 S3 在 C=1 时 TPOT 约为 S1 的 2 倍。因此**追加两组探索性条件**（明确标为探索性，不参与 H1–H4 判定）：①S3 占空比扫描 {0.25, 0.5}，负载 {1,4,16,64}，刻画"更新速率 vs 服务代价"的权衡曲线；②MPS 空间共享下的 S3，检验代价对共享机制的敏感度。
  - C2 饱和吞吐改为热身后测三次取中位数（冒烟里单次测量在两个头之间差 54%，主要是噪声）。
  - R-long 每档请求数改为约 3×并发（原为 1×），保证测到稳态而不是一波请求的排空过程。
- **2026-10-04，看到 C2 中文域 N0/N100 之后、N200 之前**：查出 AngelSlim 头的 32k 草稿词表只覆盖中文输出 token 的 42.6%（SQL 91.5%、代码 97.6%、对话 95.8%、函数调用 91.3%）。中文域因此标为**词表受限**：其接受长度和回本时间有结构性天花板，不能当作"在线学习能修的分布漂移"来解读；H4 判定时中文域的数字单列并注明，不以它单独撑起"回本时间差异 ≥10×"。
- **2026-10-04，看到 C2 SQL/代码全部检查点之后**：饱和吞吐的跨实例噪声（同一头在不同 vLLM 实例里测）被发现大于实例内三次重复的噪声（代码 N800 接受长度更高但饱和时间 +11%）。追加噪声标定作业（同一头 3 个独立实例）；在标定出来前，饱和口径的"追平/反超"判定一律视为未定。接受长度与单请求延迟不受此影响。
