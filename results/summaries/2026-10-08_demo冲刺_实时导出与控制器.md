# 腾讯 demo 冲刺：实时训练数据 + 控制器闭环（2026-10-08，进行中）

对应计划：ideas/2026-10-07_腾讯demo_计划.md。本文记录第 1、2 项的设计、已出数字和踩坑；数字随作业完成继续补。

## 1. 实时训练数据（vLLM 实时导出 → 共享内存环形缓冲 → 同卡训练进程）

**为什么必须做**：之前的闭环（10-06）训练数据是预先用 HF 前向算好的缓存，服务只是"顺序消费"；真系统里训练数据必须来自正在服务的请求本身。EAGLE-3 的输入正是目标模型第 (2,18,33) 层的 hidden states，服务每一步本来就算了，只差一个导出口。

**实现**（code/specsched/livetap.py + apply_live_tap_backport.py，打进 OSC 的 vLLM 0.27.1；主干锚点相同，可直接移植）
- 模型运行器 EAGLE 分支里，取 `target_token_ids`/`target_hidden_states`（已拼好的 3 层 aux，[T,3H] bf16）做一次非阻塞 D2H 到 pinned 池（3 槽），记 CUDA event；后台线程等 event 后按请求切块写入 `/dev/shm` 环形文件。每块 = (req_id, 起始位置, n, prompt_len, token[n] int32, aux[n×3H] bf16)。被拒绝的草稿位置按 `num_rejected_tokens` 截掉（padded 批次）或已被 `prepare_inputs` 压实。请求结束由 `_update_states` 的 `finished_req_ids` 发 FINISH 记录。
- 只有 TP rank 0 写；池满则丢整步并给该批请求发 GAP；任何异常自禁（不拖垮服务）。
- 环形文件：单写单读，记录不跨尾（PAD 填尾），`oldest_seq` 标最老完整记录，读者落后即重同步——**最新数据优先**，与调度器模拟里的 LIFO 缓冲一致。
- 训练进程 `train_head.py --mode live --tap <file>`：拼装完成的请求（位置连续性检查；抢占重算 → 保留前缀继续；真缺步 → 丢弃），CPU 侧 LIFO 缓冲（上限 60 万 token），按占空比训练，按阈值或控制器指令导出 vLLM 可加载的头。
- 环境变量开关：`VLLM_SPEC_LIVE_TAP=/dev/shm/x`（`_GB` 容量，默认 4；`_RATE` 抽样率，默认 1）。前提：`--no-enable-prefix-caching`（前缀命中的位置没有 hidden state；生产里要么关前缀缓存、要么只收完整计算的请求）。

**实测（Qwen3-8B + AngelSlim EAGLE-3 头，H100，static 模式只导出不训练）**

| 相位 | 不导出 (static) | 导出 (static_live) | 差 |
|---|---|---|---|
| A1 对话 C=16 吞吐 tok/s | 2607 | 2581 | −1.0% |
| A1 TPOT p50 ms | 5.71 | 5.74 | +0.5% |
| B 代码 C=256 吞吐 tok/s | 14461 | 14256 | **−1.4%** |
| B TPOT p50 / p99 ms | 16.93 / 22.28 | 17.18 / 22.59 | +1.5% / +1.4% |
| A2 对话 C=16 吞吐 | 2642 | 2604 | −1.4% |

导出量：B 相位 3 分钟写 68 GB、122 万条记录（≈390 MB/s），丢 1 步（池 3 槽、队列常满——写线程是瓶颈，后续可加槽/批量写）。**结论：导出代价 ≈1.5%，可以常开。**

**闭环机制验证（train_swap_live，占空比 0.5）**：B 相位开始后 ~15 s 第一批请求完成，训练器 +49/+53/+58/+69 s 导出 N100/200/400/800 并各用 0.75 s 热载；接受长度 2.13 → 3.1+；B 吞吐 16190 vs 14461（+12%，而且训练器全程没停——旧代码 live 模式不会"吃完退出"，已修成最后一次导出后退出）。

**⚠️ 这一轮数字不能用（已归档为 *_v1_pool300）**：bench 的提示池只有 300 条（`*_eval.jsonl`），9000 请求循环 30 遍；在线训练器学的是正在服务的请求，7 秒后就见过全部提示，之后的接受长度是**记忆泄漏**（3.1 远超 C2 离线学习曲线天花板 2.72）。10-06 的缓存版没有这个问题（训练用 train 切分、服务用 eval 切分，不相交），但也是 300 条循环，分布很窄。修复：`make_bench_pool.py` 从原始数据集建不重复提示池（code 16222 / zh 44776 / sql 74776 / fc 46982 / chat 16383 条，排除了流量里的 3800 条），B 相位 9000 请求全部唯一；static/train_swap/controller 三种模式用同一池重跑。

## 2. 控制器真管闭环（controller.py v2）

控制器每秒读 `/metrics`（并发 C、接受长度、直方图 TPOT、生成 tok/s）、读运营方写的域标签文件、读训练器日志（已消费请求数、缓冲 token 数），然后：
- 规则 0 停：天花板 2% 内（学到头了）；结构天花板 `gain(ceiling, C) ≤ 1`（如中文在 C=256：天花板 1.45 → 0.65×）。
- 规则 1 frontier 开关：只记录 `spec_should`（vLLM 运行时不能关投机）。
- 规则 2 SLO 内：实测 TPOT 除掉当前占空比的负荷后外推，取 0.9×SLO 内最大占空比（训练免费）。
- 规则 3 饱和：对每个占空比 d 算 K=10 s 训练窗口的数据量 → 学习曲线增量 Δa → 吞吐增量 ×(视界−K) − 现吞吐×κ(C)×d×K，视界用 lindy（当前域已持续多久，夹在 30–600 s）。**注意：饱和段的货币是吞吐，不是模拟器里的 goodput**（硬 SLO 下饱和段 goodput 恒 0，永远不会训，与 10-06 实测 +24% 矛盾）；`--sat-currency goodput` 可切回模拟器口径。论文叙事必须明说这一点。
- 导出/换头：域内消费数到 100/200/400/800…（倍增）就让训练器导出，新头出现立即 RPC 热载，之后接受长度估计重新测量。
- harness：`hotswap_run.py --mode controller --live 1`，训练器从 A1 就起（占空比 0），域标签由 harness 在相位切换时写 domain.txt。

预期行为：A1 对话 C=16 → 规则 2 免费训（对话天花板 2.37 vs 出厂 1.91）；B 代码 C=256 → 规则 3 在 lindy 视界超过 ~30–60 s 后开始训，数据受限时选低占空比；B 中文 → 规则 0 拒训，吞吐与 static 持平，而 train_swap 固定训的对照会白付 25%。

- **代码域也要诚实地说**：饱和段出厂头开投机是负收益（gain 0.88），光把投机关掉就 +13%、p99 回到 15.7 ms；训好的头保持开只再多 3 个点（16592 vs 16130），p50 更好（14.3 vs 15.5）但 p99 差（训练期尾部）。训练真正值钱的地方是 **SLO 内的对话段**：A2 TPOT 5.7→4.2 ms（−27%），以及中等负载（frontier：C=64–128 训好的头 1.5–1.9×）。所以叙事是"两个杠杆都要：饱和段先按 frontier 开关，SLO 内免费训并换头"，而不是"训练在饱和段大赚"。
- 与 10-06 缓存版（+22%，300 条池循环）相比，唯一池下固定策略 +17%——这是该报的数。**v4 控制器：+16.4%，训练占空比均值 0.074（固定策略 0.5 的 1/7），p99 全场最低**——饱和时按价值用 0.1–0.25 训、学到曲线位置就停、SLO 内免费训。v2 少拿 2.5 个点是上面四个毛病造成的。
- A2 对话段：controller TPOT 4.09 ms（static 5.63）、吞吐 +35%——A1 免费训练 + 代码训练正迁移。A1 段为此付了 TPOT 5.7→6.5 ms（规则 2 允许到 0.9×SLO=15 ms）。
- **v2 控制器的三个毛病（trace 诊断，已改成 v3 重跑 15344614）**：① `vllm bench serve` 载入 16k 条池要先 tokenize ~65 s，域标签比流量早到 → lindy 视界虚高；v3 的 regime 时钟从**观察到流量**才起算。② 饱和判别用 `C<250`，饱和时 running 在 245–256 抖 → 一会儿"SLO 内免费训"一会儿"饱和算价值"；v3 用 `waiting>0 或 running≥0.95×max_num_seqs`。③ 换域后训练器缓冲里还有 1800 条旧域（代码）序列，A2 对话段里控制器放开占空比，训练器 10 秒吞掉旧数据连发 5 次换头；v3 换域即发 `flush`，缓冲另加 60 s 保鲜期，导出最小间隔 5 s。④ 规则 3 用"已消费条数"定位学习曲线会高估剩余增益（头实际已到 2.67≈曲线 N≈1200，消费数才 600）→ v3 用实测接受率反查曲线位置；到天花板附近价值 ~30 tok/s×视界 < 损失 ~9k，自然停。

v5 在中文上超过固定策略（+13.1% vs +12.5%），训练占空比只有固定策略的 1/11：流量一到就按数据到达率训、每次换头都验证实际涨幅、到天花板停。

v4 控制器轮：bench 预处理期 52 s "no_traffic" 不训；流量一到（C=256，a=1.20）按价值规则以 0.25/0.10 训，+67 s 起换头；a 到 1.43 后 "at_ceiling" 停；**B 段占空比均值只有 0.056（固定策略 0.5 的 1/9），拿到固定策略 80% 的增益**。换域时 flush 生效（缓冲 518k→0，A2 无旧域换头）。

| **static_sched：vLLM 静态表，并发 1–64 k=3、65–256 k=0（作业 15344918）** | **16072** | **+88.5%** | **15.53 / 16.02** | （饱和段无投机） | — |

**frontier 开关实测**：同一服务、同一池，饱和段关投机吞吐 8527→16072（frontier 预测 1.8×，实测 1.885×），TPOT p50 30.5→15.5、p99 36.5→16.0（回到 SLO 内！）；A 段（C=16，k=3）不变。**对中文这类域，"关投机"是比"训头"大一个数量级的杠杆（+88% vs +10～12%）**，而 vLLM 0.27 已经有静态的按批大小 k 表（`num_speculative_tokens_per_batch_size`），缺的只是让控制器按域/按头把阈值放对地方（代码域训好后 a=2.67、gain 1.15，饱和时就该保持开；静态表做不到按头变）。代码域同款对照已排队。

原剧本：中文天花板 1.45 在 C=256 的 frontier 上只有 0.65×，"训了也赢不了，控制器拒训"。实测固定训练反而 +12.5%——因为 **vLLM 运行时关不掉投机**：投机既然一直开着，把接受长度从 1.23 拉到 1.42 就是实打实的 +12%（frontier 预测 +18%，扣掉训练期代价）。"拒训"只在引擎能运行时关投机时才对：那时正确动作是关投机（frontier：无投机比出厂头投机快 1.8×，+54%），训练才是白费。所以控制器的结构天花板判别必须以引擎能力为条件：`--spec-switchable 1` 才拒训，vLLM 今天是 0 → 走价值规则照训。**这是给腾讯的一个具体需求点：引擎要有运行时投机开关（或按负载的投机 token 数调度表），否则中文这类词表受限的域在饱和时白白慢 1.8×。** 中文 controller 轮用 v4（spec_switchable=0）跑。

MoE 上控制器比固定 0.5 少 3 个点：两者学到同样的 2.94，但控制器的导出按域内消费数 100/200/400 倍增、第三次换头在 +130 s（固定策略 +65 s 就换完四个头），而 B 段只有 165 s——适应完成得晚，剩给"赚回来"的时间短。训练花费只有固定策略的 1/6。窗口拉长（真实流量切换以分钟计）差距会消失；要压时间可把首个导出阈值从 100 降到 50。

MoE 出厂头起点高（2.62），增益比 dense 小但同样成立；头小，热载 0.32 s；导出 33.6 GB（3H=6144）。对话段 MoE 没标定曲线 → 控制器按"未知域不训"（正确且诚实）。

**v4 控制器在 MoE 上比固定 0.5 少 3 个点的原因（trace）**：规则 3 按"下一个 10 s 窗口的净价值"选占空比，数据充足时也只选 0.10，于是用 170 s 慢慢学到 2.89；固定策略 65 s 就学到 2.94 然后全速服务。同样的训练 token，早换上头多赚的服务时间才是价值——该用"到目标的时间"口径：占空比与数据到达率匹配（训练不比数据来得快），净价值 = 终态吞吐增益 × (视界 − 训练时长) − 训练期损失；另加"换头后没涨就收敛停"（N727 换上 2.89→2.88）。改成 v5 后三组控制器重跑。

## 2.5 运行时投机开关（10-08 晚，用户指出规则 1 只记录不执行）

vLLM 0.27 运行时没有投机开关，之前规则 1 只写 `spec_should`。补上：`apply_spec_switch_backport.py` 给 runner 加 `set_speculation(enabled)`（worker 透传，走已有的 `POST /collective_rpc`）：关掉时 runner 不再出草稿，调度器下一步起就按普通一 token 一步解码；drafter 与权重留在显存里，打开即下一步生效；关着时 live tap 改从目标模型自己的输出继续导出（只取没带草稿的步，保证位置全部已提交）。控制器 v6 `--spec-switch 1`：规则 1 真执行（连续 3 tick 同向 + 10 s 最小间隔；换头时若关着则开 8 s 探测新头接受率）；规则 3 的目标吞吐取"开/关两种模式的较优者"。

**第一版（只在 worker 关）是错的，实测教训**：on→off→on 单测（15347872）：关掉后吞吐 14168→**7633（−46%）**，接受长度 1.00、草稿计数反而翻倍——padded 模式下调度器照样给每个请求预留 k 个草稿槽（`pad_spec_decode`，占位 −1），worker 不出草稿槽里就是垃圾，全被拒绝，等于白付 k+1 倍验证。vLLM 自己"输入装不进 drafter"的路径也是这么付的（罕见情况可以接受，开关不行）。
**正确做法**：开关有两半——调度器 `spec_enabled=False` 时不再调度草稿槽（`num_spec_tokens_to_schedule=0`、不 pad），worker 不再出草稿；`EngineCore.collective_rpc` 拦截 `set_speculation` 把两半同步切，仍走已有的 `/collective_rpc`。0.27.1 回移植（scheduler/core/runner/worker 四处）+ 主干分支 d1154a8。另一个 bug：关投机那一步批里还带着上一轮草稿时簿记仍需有效采样数，hook 要镜像"装不进 drafter"路径只做簿记不出草稿（否则断言崩）。
**调度器级开关实测（15348478，同一服务 on→off→on，代码池 C=256）**：开 13989 tok/s（a=2.14，TPOT 16.8/21.5）→ **关 15459（+10.5%，TPOT 15.0/15.2，草稿数 0）** → 再开 13981（完全恢复）；切换耗时 10 ms / <1 ms。中文同款：开 8461 → **关 15675（+85%，TPOT 29.6→15.0、p99 35.9→16.0）** → 再开 8477。Excel 表 R2_spec_switch。
**中文控制器开关版（15348479，`controller_sw_live`）**：B 段吞吐 **15578（+82.7% vs 不训练 8527）**，TPOT p50 15.7 / p99 21.2（回 SLO 内）；控制器行为：流量一到判定 gain(1.2, 256)<1 → 关投机；结构天花板 → 不训（174 tick，占空比均值 0.012）；A1/A2 对话段 SLO 内免费训并换头（A2 TPOT 4.13 vs 5.7）。这就是三条判别在一条时间线上全部兑现。
作业：开关单测重跑 15348478（code+zh）；中文控制器开关版 15348479（`controller_sw_live`）；主干测试 15348503。代码域开关版（15347873，worker 版）：A1 免费训出的头让 B 段一开始就 a=2.47、gain 1.07>1，控制器判定不关，+16.1%（与 v5.1 一致）。预期中文：饱和关（≈+88%）且结构天花板判定不训。
